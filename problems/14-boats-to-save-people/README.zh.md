### 14. Boats to Save People

> *每艘船最多坐两人，总重不能超过限重。求最少需要多少艘船。*

**🧩 算法**
先排序。左指针指向最轻的人，右指针指向最重的人。每一轮，最重的人**必须**上船——无论如何都占一个位置。唯一的问题是：最轻的人能不能顺便挤进去？

- 如果 `最轻 + 最重 ≤ limit` → 两人一起走。`left += 1, right -= 1, boats += 1`。
- 如果 `最轻 + 最重 > limit` → 最重的人跟谁都配不了（最轻的已经是他的最佳搭档了）。最重的人单独坐。`right -= 1, boats += 1`。

最重的人是"必须立刻处理的主角"。最轻的人只是在检查：*"我能搭便车吗？"* 每一轮至少淘汰一个端点，把指数级的决策树压成线性。

```python
class Solution:
    def numRescueBoats(self, people: list[int], limit: int) -> int:
        people.sort()

        left, right = 0, len(people) - 1
        boats = 0

        while left <= right:
            if people[left] + people[right] <= limit:
                left += 1
            right -= 1
            boats += 1

        return boats
```

> 时间 $O(n \log n)$（瓶颈在排序）· 空间 $O(1)$

更深的原理：**先处理最难的约束。** 最重的人是瓶颈——他最难配对、最可能单独占船、最限制后续选项。先处理他，下游的一切就变简单了。最轻的人——容易的情况——变成灵活的填充物，哪里有容量就塞哪里。

**🏢 职场**
面对资源分配问题——预算、人手、截止日期——本能可能是先处理简单任务、找感觉、体验产出感。**别。**

难约束就是船上的最重的人。它需要三个审批的项目、截止日期最紧的客户、卡住一切的依赖项。先处理它。它*必须*被解决——不存在它自己消失的场景。唯一的问题是能不能顺便捎上简单的。

瓶颈一旦解决，剩下的任务——轻的——就灵活得多了。它们填入剩余的任何容量。但如果你先把简单的用掉了，你可能浪费了唯一能跟瓶颈配对的资源，让难问题孤立无援、单独占船。

**🌍 人生**
**遇到问题应该先考虑限制，然后先解决瓶颈。之后简单的事情才容易被灵活规划——而不是先用掉灵活性再去面对约束。**

本能是这样的：先清掉简单的事。把小任务做完、收件箱清零、感受势头。感觉很负责。其实不是。

最难的问题——最重的人——才是真正决定你需要多少艘船的那个。再多的简单任务清理也改变不了这一点。真正改变的是：当难问题被处理之后，简单任务是否还能作为灵活填充物。如果你已经把最轻的人——你的备用精力、空闲下午、善意缓冲——用在了容易的胜利上，你就失去了唯一可能跟重约束配对、省下一艘船的资源。

成熟的做法：按严重程度排列你的约束。先处理最重的。然后让轻的、灵活的任务填入剩余的任何容量。这不仅最小化总船数——也意味着简单部分真的简单，因为未解决的难问题的阴影不再笼罩其上。

**⚠️ 反模式**
*"先把简单的清掉，找找感觉。"* 那就是把两个最轻的人配在一起。感觉很高效——看到船在填满、任务在完成。但你刚刚浪费了最轻的人——唯一可能跟最重的人配对的那个——用在一组本可以之后再配的搭档上。现在最重的人落单了，你多花了一艘船。简单的任务从来不是问题；它们是*解决方案*——让难问题用更少的船就解决的灵活填充物。最后用它们，而不是最先。
