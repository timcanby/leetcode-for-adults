### 26. Merge Sort

> *把数组对半切开，各自排序，再把两个有序的一半合并回去。*

**🧩 算法**
归并排序不靠扫描、交换、插入或选择排序。它靠**分治**：把问题对半切，各自独立解决，再把结果缝合。而且它*递归地*做这件事——每一半被切成四分之一，每个四分之一切成八分之一——直到碎片小到平凡（一个元素，已经有序）。然后沿链向上合并，两个有序的一半一组，直到整个数组是一个有序整体。

```python
def merge_sort(nums):
    if len(nums) <= 1:
        return nums

    mid = len(nums) // 2
    left = merge_sort(nums[:mid])
    right = merge_sort(nums[mid:])

    ans = []
    i = j = 0

    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            ans.append(left[i])
            i += 1
        else:
            ans.append(right[j])
            j += 1

    ans.extend(left[i:])
    ans.extend(right[j:])
    return ans
```

> 时间 $O(n \log n)$——永远如此，有保证 · 空间 $O(n)$

更深的原理：**大问题只是你还没对半切的小问题。**

精妙之处在递归——*自相似性*。函数在同一个问题的更小版本上调用自己。它不需要知道怎么排序一百万个元素。它需要知道怎么排两个元素（平凡：比较并排序）和怎么合并两个有序列表（走两边，取较小的）。就这。切 → 递归 → 合并。百万级排序通过 $\log_2(n)$ 层对半切自己搞定。

而保证是：**归并排序的 $O(n \log n)$ 不只是典型——是最坏情况。** 跟 quicksort 在坏输入上退化到 $O(n^2)$ 不同，归并排序的性能*由数学结构保证*。每层做 $O(n)$ 的工作。恰好 $\log_2(n)$ 层。没有输入能打破它。成本由大小决定，不由排列决定。混沌不收税。保证来自结构——每次对半切，每次线性合并——而结构不说谎。

代价是：**归并排序为它的 $O(n \log n)$ 保证付 $O(n)$ 空间。** 它需要一个缓冲区来放合并结果。不像原地排序在数组内部交换，归并排序复制和组合。保证需要内存。你在为"没有输入会让你意外"的确定性付费。

**🏢 职场**
最大的项目不是一个人在一张桌上解决的。它们靠**分治**解决：把项目对半切，每半交给一个能独立处理的团队，然后合并结果。

归并排序的智慧：**你不需要知道怎么解决整个问题。你需要知道怎么切，和怎么合并解决方案。** 如果你能把一个问题切成两个独立的子问题，并且能把两个有序的解合并成一个连贯的答案，那问题的大小不重要——它只是多加一层递归。

而保证是：**一个结构良好的团队的性能是 $O(n \log n)$，不管项目难度如何。** 如果你的组织每一层都能切工作、合并结果，总成本由结构决定，不由内容决定。难的项目需要更多层（更深的递归），但每层做同类的工作：切、解、合并。没有项目——无论多混乱——在切得干净、合并得称职时把结构退化到 $O(n^2)$。结构保护你免受混沌。

但代价是：**归并排序为保证付空间。** 在组织里，"空间"是协调开销——保持两个团队同步的沟通成本、让每半的输出可合并的文档成本。分治不免费；它需要一个缓冲区——会议、规格、接口——来承载合并。跳过缓冲区，你得到两个合不到一起的有序半边。合并不是因为半边错了而失败，而是因为它们在造的时候不知道怎么组合而失败。

**🌍 人生**
最大的人生问题——"建一份事业"、"养一个家庭"、"找到你的使命"——感觉不可能，因为它们是整个数组的问题。你不能通过比较每对来排序一百万个元素。但如果你把问题对半切，再切，再切，直到每块小到能拿在手里——你能。

人生版的归并排序：**别试图解决整个问题。切它。** "建事业"变成"搞清我擅长什么"+"搞清市场需要什么"。各自再切："我擅长什么"变成"我有什么技能"+"我想学什么技能"。一直切到每块是一个单一决定："上这门课"、"读这本书"、"投这个岗位"。平凡可解。然后向上合并：把技能合成一个画像，把画像和市场需求合成一个职业方向。

而保证是：**结构保护你免受混沌。** 不管问题感觉多压垮性，如果你能对半切并合并解，总成本是 $O(n \log n)$——不是 $O(n^2)$。你从不同时面对整个问题。你面对 $\log_2(n)$ 层，每层只是：切，解决更小的块，合并。递归就是保护。层级就是缓冲。你不需要把整个问题装在脑子里——你一次拿一层，结构处理其余。

而代价——空间成本：**归并排序要求你保存中间结果。** 你不能只切然后忘。每半的解必须被*保存*——在记忆里、在笔记里、在计划里——直到合并发生。切了不记中间解不是归并排序；那只是撒。人生分治的空间成本是*追踪进度*的成本：写日记、做计划、复盘。你付 $O(n)$ 空间来保存碎片以便合并。跳过它，你有两个有序的半边却无法组合——人生的两半合不成一个整体。

**⚠️ 反模式**
*"我把问题切成小块然后一个个解决。"* 那不是归并排序——那只是……做待办清单。缺的是**合并**。把问题切成子问题只是算法的一半。另一半——让它变成 $O(n \log n)$ 而非 $O(n^2)$ 的一半——是*把解了的子问题组合成一个连贯整体*。如果你把项目切成任务，解决每个任务，但从不整合结果，你有一堆有序的碎片，不是一个有序的数组。合并是大多数项目失败的地方：不在切，不在解，而在*组合*。合并需要知道碎片怎么拼——它们共享什么接口、按什么顺序、两个有序半边相遇时什么冲突会出现。切很简单。合并是艺术。如果你能切不能合，你在用 $O(n)$ 创造碎片、用 $O(n^2)$ 清理混乱。合并不是算法的灵魂——也是项目的灵魂，人生的灵魂。
