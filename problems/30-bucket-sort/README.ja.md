### 30. Bucket Sort

> *要素を値の範囲でバケットに分散し、各バケットをソートし、結合する。*

**🧩 アルゴリズム**
バケットソートは配列をソートしない——**散らす**——各バケットに個別にソートさせ、**集める**。魔法は散らしにある：要素は値の範囲でバケットにルーティングされるので、各バケットは似た小さなスライスしか持たない。バケット内のソートは自明だ——似た数要素、どんな方法でも簡単。ソートの難しい部分——広い範囲にわたる不似な要素の比較——は*散らしによって消除される*。

```python
def bucket_sort(nums, bucket_size=5):
    if len(nums) < 2:
        return nums

    lo, hi = min(nums), max(nums)
    bucket_count = (hi - lo) // bucket_size + 1
    buckets = [[] for _ in range(bucket_count)]

    for x in nums:
        buckets[(x - lo) // bucket_size].append(x)

    ans = []
    for bucket in buckets:
        bucket.sort()
        ans.extend(bucket)

    return ans
```

> 時間 $O(n + k \cdot \frac{n}{k} \log \frac{n}{k})$——一様分布で $O(n)$ · 空間 $O(n)$

より深い原理：**全体をソートするのではない——部分をソートし、散らしが部分をソート可能にする。**

散らしがアルゴリズムの魂だ。ソートが始まる前、配列は既に*部分的に整序*している：バケット $i$ の全要素はバケット $i+1$ の全要素より小さい。それはソートの結果ではなく——*ルーティング*の結果だ。散らしは一つの算術演算（この値はどのバケットに属するか？）で粗い順序を課し、ソートは各バケット内の*細かい*順序だけを処理する。難しい問題——大局的ソート——は散らしの動作によって多くの簡単な問題——局所的ソート——に分解される。

そして美しさ：**分布が一様なら、バケットソートは $O(n)$ だ。** 各バケットは $\approx n/k$ 要素を持ち、バケット内のソートは範囲が狭いから速い。総仕事量は $n$ の散らし + $k$ 回の各 $\approx n/k$ のソート——一様分布で $O(n)$ に簡約。分布の均一さ*が*パフォーマンス保証だ。カオスなデータが一つのバケットに固まれば $O(n \log n)$ に劣化——一つの大きなバケットをソートしている。アルゴリズムの効率はコードではなく、データの*形*にある。

そしてトレードオフ——バケットサイズ：**バケットが少なすぎると一つの大きな配列をソートする；多すぎると空のコンテナにオーバーヘッドを払う。** バケットサイズが全てを決定する。大きなバケット：ルーティングのオーバーヘッドが小さいがバケット内のソートが多い。小さなバケット：オーバーヘッドが大きいがソートは自明。最適はデータが適切な数のバケットに均等分布している時——そして*それは*データを理解することに依存する。バケットソートは*分布を理解する*ことに対して報いる。データが一様だと知っていれば、正確に命中できる。分布に盲目なら、推測する——悪い推測は一つの過負荷バケットと $n-1$ の空バケットを意味する。

**🏢 職場**
全社的な問題を大局的に攻撃しない。**散らす**——各イシュー、各タスク、各決定をその範囲を所有するチームにルーティングする——それから各チームに自分のスライスをソートさせる。

散らしが組織設計だ。仕事が始まる前、イシューは既に*部分的に整序*している：チーム $i$ のドメインの各イシューはチーム $i+1$ のどれよりチーム $i$ に近い。それは協力の結果ではなく——*ルーティング*の結果だ。組織図が粗い順序を課し（どのチームがどの範囲を所有するか？）、チームはドメイン内の*細かい*順序だけを処理する。難しい問題——全チームにわたる大局的優先順位——は散らしの動作によって多くの簡単な問題——各チーム内の局所的優先順位——に分解される。

そして美しさ：**ワークロードが均等分布なら、組織は $O(n)$ で動く。** 各チームは $\approx n/k$ のイシューを持ち、チーム内のソートは範囲が狭いから速い。分布が均等なら——過負荷のチームもアイドルのチームもなく——組織全体が最遅チームの速度で動く、それは速い。分布がカオスなら——一つのチームが 90% を持ち、残りの $k-1$ が空——組織は過負荷チームの $O(n \log n)$ に劣化。ボトルネックはアルゴリズムではない；*塊*だ。

そしてトレードオフ——チームサイズ：**チームが少なすぎると各々が大きなバックログをソートする；多すぎると空のチームに調整オーバーヘッドを払う。** バケットサイズ——チームのスコープ——が全てを決定する。大きなチーム：ルーティングのオーバーヘッドが小さい（ハンドオフが少ない）が内部ソートが多い。小さなチーム：オーバーヘッドが大きいが内部ソートは自明。最適はワークロードが適切な数のチームに均等分布している時——そして*それは*組織の問題分布を知ることに依存する。バケットソートは*仕事の分布を理解する*ことに対して報いる。イシューが一つのドメインに塊になると知っていれば、そこにより多くのチームを配分する。盲目なら、等しいチームを作り、一つが溺れる。

**🌍 人生**
人生全体を大局的に攻撃しない。**散らす**——各コミットメント、各プロジェクト、各人間関係をそれが属する「バケット」にルーティングする——それからバケット内でソートする。

散らしが人生設計だ。ソートが始まる前、人生は既に*部分的に整序*している：「健康」バケットの各コミットメントは「キャリア」バケットのどれより「健康」に近い。それは優先順位付けの結果ではなく——*ルーティング*の結果だ。粗い順序を課し（これはどのライフドメインに属するか？）、各ドメイン内で*細かい*順序をソートする。難しい問題——「私の人生で最も重要な一つは何か？」——は散らしの動作によって多くのより簡単な問題——「私の健康/キャリア/人間関係/財務で何が最も重要か？」——に分解される。

そして美しさ：**人生が均等分布なら、$O(n)$ で動く。** 各ドメインは管理可能な数のコミットメントを持つ。ドメイン内のソートは範囲が狭いから速い。どのドメインも過負荷でなく空でない時——精力、時間、注意がドメインに概ね均等に分散されている時——人生は $O(n)$ に感じる。滑らかで、線形で、管理可能。一つのドメインが塊になれば——仕事が 90% を占め、健康、人間関係、財務が空——人生は過負荷バケットの $O(n \log n)$ に劣化。全精力を一つの巨大な仕事バケットのソートに使い、残りに埃が積もる。ボトルネックは努力ではない；*塊*だ。

そして知恵：**散らしはソートの前に来る。** 優先順位をつける前、最適化する前、「人生を整理する」ことを試みる前——散らせ。各々をそのバケットにルーティングせよ。*それから*バケット内でソートせよ。散らしの動作は*理解*の動作だ——それは範囲を知ること、分布を知ること、何が一緒に属するかを知ることを必要とする。散らしをスキップすれば、一つの巨大な無差別の山をソートし、$O(n)$ のべきものに $O(n \log n)$ を払う。先に散らせ。それからソートせよ。散らしはウォームアップではなく；アルゴリズムだ。

**⚠️ アンチパターン**
*「全てを一つの大きなリストで優先順位付けする。」* それは配列全体の比較ソートだ——一つの大きなバケット、$O(n \log n)$、範囲は人生の全幅。歯医者の予約とキャリアの決断と友人へのテキストを同じリストに入れ、同じやり方で比較している。散らしが*この不条理を防ぐ*：まずバケットにルーティングし（健康、キャリア、人間関係）、それからバケット内でソートする。歯医者の予約は他の健康タスクとのみ比較される——五年計画とは比較されない。キャリアの決断は他のキャリアの動きとのみ比較される——今日テキストを返すかとは比較されない。散らしは、単一の優先度リストを狂わせるドメイン間比較を排除する。散らしなしでは、$O(n \log n)$ の山の中でリンゴと都市と歯医者の予約を比較し、計算された「優先度」は無意味——ドメイン間は比較できないから。先に散らせ。それからソートせよ。分解*が*解決策だ。
