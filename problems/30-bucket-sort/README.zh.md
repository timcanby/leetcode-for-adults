### 30. Bucket Sort

> *把元素按范围分散到桶里，每个桶内排序，然后拼接回去。*

**🧩 算法**
桶排序不排数组——它把数组**散**进桶里，每个桶单独排，然后**收**回来。魔法在散：元素按值范围路由到桶，所以每个桶只装一小片相似的元素。桶内排序是平凡的——几个相似的元素，任何方法都好排。排序中难的部分——跨大范围比较不相似的元素——*被分散这一步消除了*。

```python
def bucket_sort(nums, bucket_size=5):
    if len(nums) < 2:
        return nums

    lo, hi = min(nums), max(nums)
    bucket_count = (hi - lo) // bucket_size + 1
    buckets = [[] for _ in range(bucket_count)]

    for x in nums:
        buckets[(x - lo) // bucket_size].append(x)

    ans = []
    for bucket in buckets:
        bucket.sort()
        ans.extend(bucket)

    return ans
```

> 时间 $O(n + k \cdot \frac{n}{k} \log \frac{n}{k})$——均匀分布时 $O(n)$ · 空间 $O(n)$

更深的原理：**你不排整体——你排部分，分散让部分变得可排。**

散是算法的灵魂。在任何排序发生之前，数组已经被*部分有序*了：桶 $i$ 里的每个元素都小于桶 $i+1$ 里的每个元素。那不是排序的结果——是*路由*的结果。散用值本身（一次算术运算：这个属于哪个桶？）施加了粗序，而排序只需处理每个桶内的*细*序。难的问题——全局排序——被散的动作分解成许多容易的问题——局部排序。

而美妙之处：**当分布均匀时，桶排序是 $O(n)$。** 每个桶装 $\approx n/k$ 个元素，桶内排序快因为范围小。总工作量是 $n$ 次散 + $k$ 次各 $\approx n/k$ 的排序——均匀分布时简化为 $O(n)$。分布的均匀性*就是*性能保证。混沌数据挤进一个桶则退化到 $O(n \log n)$——你回到了排一个大桶。算法的效率不在代码里；在数据的*形状*里。

而代价——桶大小：**桶太少你在排一个大数组；桶太多你在为空容器付开销。** 桶大小是决定一切的参数。大桶：路由开销小但桶内排序多。小桶：路由开销大但排序平凡。最优是数据均匀分布在合适数量的桶里——而*那*取决于了解你的数据。桶排序奖赏你*理解分布*。如果你知道数据是均匀的，你能精准命中。如果你对分布一无所知，你在猜——猜错意味着一个超载桶和 $n-1$ 个空桶。

**🏢 职场**
你不会全局攻击一个全公司的问题。你**散**——把每个问题、每个任务、每个决策路由到拥有它范围的团队——然后让每个团队排自己的那片。

散就是组织设计。在任何工作发生之前，问题已经被*部分有序*了：团队 $i$ 领域里的每个问题都比团队 $i+1$ 的更接近团队 $i$。那不是协作的结果——是*路由*的结果。组织架构施加了粗序（哪个团队拥有哪个范围？），团队只需处理领域内的*细*序。难的问题——跨所有团队的全局优先级——被散的动作分解成许多容易的问题——每个团队内的局部优先级。

而美妙之处：**当工作负载均匀分布时，组织以 $O(n)$ 运转。** 每个团队持 $\approx n/k$ 个问题，团队内排序快因为范围窄。当分布均匀——没有团队超载、没有团队闲置——整个组织以最慢团队的速度运转，那很快。当分布混沌——一个团队持 90% 的问题，其余 $k-1$ 个空——组织退化到超载团队的 $O(n \log n)$。瓶颈不是算法；是*拥塞*。

而代价——团队大小：**团队太少每个在排一个大 backlog；团队太多你在为空团队付协调开销。** 桶大小——团队 scope——决定一切。大团队：路由开销小（交接少）但内部排序多。小团队：路由开销大（交接多）但内部排序平凡。最优是工作负载均匀分布在合适数量的团队——而*那*取决于了解你组织的问题分布。桶排序奖赏你*理解工作分布*。如果你知道问题聚集在一个领域，在那里分配更多团队。如果你一无所知，你创建等大的团队然后其中一个淹死。

**🌍 人生**
你不会全局攻击整个人生。你**散**——把每个承诺、每个项目、每段关系路由到它属于的"桶"——然后桶内排。

散是人生设计。在任何排序之前，你的人生已经被*部分有序*了："健康"桶里的每个承诺比"职业"桶里的任何东西都更接近"健康"。那不是排序的结果——是*路由*的结果。你施加了粗序（这属于哪个生活领域？），然后在每个领域内排*细*序。难的问题——"我人生中最重要的一件事是什么？"——被散的动作分解成许多更容易的问题——"我的健康/职业/关系/财务中什么最重要？"

而美妙之处：**当人生均匀分布时，它以 $O(n)$ 运转。** 每个领域持有可控数量的承诺。领域内排序快因为范围窄。当没有领域超载、没有领域空闲——当你的精力、时间、注意力大致均匀地分布在各领域——人生感觉是 $O(n)$。流畅、线性、可控。当一个领域拥塞——工作占 90%，健康、关系和财务都空着——人生退化到超载桶的 $O(n \log n)$。你把所有精力花在排一个巨大的工作桶上，其余积灰。瓶颈不是你的努力；是*拥塞*。

而代价——桶大小：**生活领域太少每个是超载的 backlog；太多你在维护空类别上付开销。** 桶大小——你的生活领域有多细——决定一切。粗桶（"工作"vs"生活"）：开销小但每个桶重。细桶（"晨间例行"vs"锻炼"vs"备餐"）：开销大但每个平凡可管。最优是你人生的承诺均匀分布在合适数量的领域——而*那*取决于了解*你的*分布。

而智慧是：**散在排之前。** 在你排优先级之前、在你优化之前、在你试图"把人生理顺"之前——先散。把每样东西路由到它的桶。*然后*桶内排。散的动作是*理解*的动作——它要求了解范围、了解分布、了解哪些东西属于一类。跳过散，你在排一大堆无差别的东西，用 $O(n \log n)$ 付本该 $O(n)$ 的。先散。后排。散不是热身；散就是算法。

**⚠️ 反模式**
*"我把所有东西按优先级排成一个大清单。"* 那是对整个数组的比较排序——一个大桶，$O(n \log n)$，范围是你人生的全跨度。你在把一个牙科预约和职业决策和给朋友发短信放在同一个清单里、用同样的方式比较。散*阻止*了这种荒谬：先路由到桶（健康、职业、关系），然后桶内排。牙科预约只和其他健康任务比——不和你的五年计划比。职业决策只和其他职业举动比——不和今天要不要回短信比。散消除了让单一优先级清单变得疯狂的那些跨领域比较。没有散，你在 $O(n \log n)$ 的一堆里比较苹果和城市和牙科预约，算出的"优先级"毫无意义——因为领域之间不可比。先散。后排。分解*就是*解决方案。
